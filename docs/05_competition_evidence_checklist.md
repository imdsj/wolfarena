# WolfArena 比赛记录与证据保留清单

本文用于保留比赛评审需要的开发证据，并区分“Git 中应公开的内容”和“只能私密保存的材料”。

## 1. 必须保留的主线记录

| 类别 | 要保留什么 | 存放位置 | 用途 |
| --- | --- | --- | --- |
| Git 历史 | 每次有意义修改的 commit、作者和日期 | 本地仓库及 GitHub/Gitee 远程仓库 | 证明项目真实演进和团队贡献 |
| 规则 | 带编号、稳定且可测试的规则文档 | `docs/` | 对照游戏引擎函数和测试 |
| 代码 | 游戏引擎、后端、前端和训练代码 | `backend/`、`frontend/` | 展示可运行产品 |
| 测试 | 测试源码和通过记录 | `tests/`，测试记录可放 `docs/evidence/` | 证明规则不是只写在文档里 |
| 决策 | 重要规则变化、技术取舍及原因 | `docs/` | 答辩时解释为什么这样做 |
| 运行说明 | 安装、启动、测试和演示步骤 | `README.md` | 让评委和队员可以复现 |

## 2. 最终比赛材料

根据项目计划，正式提交至少需要保留以下材料：

| 材料 | 最低要求 | 当前状态 |
| --- | --- | --- |
| 代码仓库 | GitHub/Gitee 可访问，保留真实 Git 历史 | 只有本地仓库，尚未配置远程地址 |
| README | 项目介绍、依赖、启动方式、测试方式和限制 | 已建立基础版本 |
| 演示视频 | 5 至 8 分钟、1080p、普通话讲解 | 未开始 |
| 技术文档 | PDF，不超过 30 页 | 未开始 |
| 在线演示 | 公网地址、测试账号或免登录入口 | 未开始 |
| 模型卡 | 算法、数据、指标、限制和版本 | 未开始 |
| 团队约定 | 成员分工、贡献和成果归属 | 已有计划模板，需队员确认 |

平台中的报名、缴费或提交成果应另外保存截图、页面另存或回执。它们是参赛流程记录，不能代替 Git 仓库中的代码历史。

## 3. AI 与技术评分证据

| 证据 | 建议产物 |
| --- | --- |
| DeepSeek 集成 | 脱敏后的请求结构、响应结构、失败重试和超时记录 |
| Agent 工作流 | Agent 输入、结构化决策、服务端校验和最终动作的完整链路 |
| RAG | 知识库来源清单、检索案例、引用规则和失败案例 |
| Function Calling | 工具定义、调用示例、权限校验和非法调用拒绝记录 |
| 安全层 | Prompt 注入测试、越权读取测试、JSON 校验和密钥扫描记录 |
| Q-learning | 状态、动作、奖励定义，训练配置、固定 seed、训练日志摘要和指标 |
| 训练对照 | 同 seed 的训练前后胜率、动作分布和策略差异 |

不要把大段未经脱敏的模型对话直接提交。保留能够复现结果的结构化记录和代表性案例即可。

## 4. 前端与用户体验证据

保留以下材料：

- 每个主要页面在各开发阶段的截图。
- 手机 390px 宽度下的创建房间、发言、投票和结果页面截图。
- 观战密码、玩家死亡视角和游戏结束揭示身份的截图。
- 浏览器控制台错误清理前后的对比。
- 手机端、桌面端完整操作录屏。
- 外部用户试用记录、问题编号和修复结果。

截图前必须关闭开发者工具中的密钥、服务器地址中的敏感参数和个人隐私。

## 5. Git 记录规范

每次提交应说明完成了什么，例如：

```text
chore: initialize WolfArena project structure
docs: define nine-player game rules v1
feat: add reproducible game creation and role assignment
test: cover fixed roster and seeded role assignment
```

不建议整个开发周期只有一次 `update` 提交。真实、连续、可解释的提交历史是比赛材料的一部分，禁止伪造提交时间或作者。

在重要节点创建可读标签，例如：

```powershell
git tag -a v0.1-rules-engine -m "Rules and game creation baseline"
```

标签应指向已经通过测试的提交。

## 6. 必须私密保存的内容

以下内容可以用于团队内部或平台提交流程，但不得进入公开仓库：

- `.env`、真实 API Key 和访问令牌。
- 服务器密码、SSH 私钥和宝塔登录信息。
- 身份证、手机号、真实个人信息和未脱敏用户数据。
- 报名费支付凭证原图和个人中心页面。
- 未脱敏的真人玩家对局日志。

真实环境文件应放在仓库外或本地 `.env`。平台回执和个人材料建议保存在加密压缩包或私人云盘，并保留第二份备份。

## 7. 大文件与训练结果

`training_runs/`、数据库和日志默认被忽略，避免仓库膨胀或意外泄露。需要长期保留时：

1. 原始训练文件保存在仓库外，并记录文件日期、seed 和配置。
2. 只挑选小型 CSV、JSON 指标和图表放入 `docs/evidence/`。
3. 公开前检查是否含真人信息、密钥或服务器路径。
4. 为重要原始结果计算校验值，放到文字清单中。

## 8. 每个里程碑要保存的快照

每次完成一个可验收版本，至少保存：

```text
Git commit hash
完成日期
测试命令
测试通过数量
主要功能截图
已知问题
下一里程碑
```

建议放入 `docs/evidence/YYYY-MM-DD_里程碑名称.md`。测试输出可以复制成文本，但必须对应明确的 commit。

## 9. 提交前检查

- [ ] 仓库已推送到团队控制的 GitHub/Gitee 地址。
- [ ] 评委访问仓库不需要临时联系开发者授权。
- [ ] Git 中有连续、真实、可解释的提交。
- [ ] README 的启动和测试命令可以复现。
- [ ] 测试全部通过并保存对应 commit 的记录。
- [ ] 仓库和最终视频中没有真实 API Key、密码和个人隐私。
- [ ] 技术文档、视频、在线演示和模型卡已保存备份。
- [ ] 平台报名、提交成功页面和回执已截图保存。
- [ ] 最终提交前创建版本标签并备份仓库。
