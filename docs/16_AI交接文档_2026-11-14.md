## 1. 项目是什么

**WolfArena（狼域）**，**第九届传智杯 AI Web 网页开发挑战赛 B 组**项目。

一句话定位：把**九人狼人杀**、**可解释的 AI Agent 行为**、**可复现的策略训练**放在同一个 Web 平台里。

不是普通狼人杀网页。比赛要现场证明的是"AI 真的在思考"，所以整个系统的重心在**可解释**和**可复现**上：

- 九个 AI 座位是**九个独立 Agent**（各自有记忆、计划、怀疑对象），不是同一个策略换角色提示词
- 四种人格真实改变目标选择、发言和战术使用
- Agent 能规划、调用白名单工具，并用事件证据解释决策
- RAG 有来源、有检索过程、有消融对照
- 战术能提交、训练、评测、审批、回滚
- 观战与赛后能看懂 AI 为什么这样行动

### 1.1 九人局配置

| 角色 | 代码标识 | 数量 | 阵营 | 能力 |
| --- | --- | --- | --- | --- |
| 狼人 | `werewolf` | 3 | `wolf` | 夜间两轮内部发言、狼队长选刀（可自刀/空刀）、白天可自爆 |
| 村民 | `villager` | 3 | `good` | 无主动技能，公开发言 + 投票 |
| 预言家 | `seer` | 1 | `good` | 每晚查验一名存活玩家阵营 |
| 女巫 | `witch` | 1 | `good` | 解药毒药各一次，**同一晚至多使用一种** |
| 猎人 | `hunter` | 1 | `good` | 被狼杀且未被救可开枪；**被毒不能开枪**；被放逐可开枪 |

规则用稳定编号供代码和测试引用：`GAME-`（游戏）、`VIEW-`（可见性）、`WOLF-`（狼队）、`DAY-`（白天）、`DESTRUCT-`（自爆）、`VOTE-`（投票）。改规则时**必须同步改编号对应的测试**。

### 1.2 阶段机（13 个状态）

```text
INIT
 ├ 夜：NIGHT_WOLF_DISCUSSION_R1 → R2 → NIGHT_WOLF_KILL
 │      → NIGHT_SEER_CHECK → NIGHT_WITCH_ACTION
 │      → NIGHT_RESOLUTION → NIGHT_HUNTER_SHOT
 ├ 判：CHECK_WINNER（未结束则天亮）
 ├ 昼：DAY_ANNOUNCEMENT → DAY_LAST_WORDS → DAY_DISCUSSION
 │      → （可自爆）→ VOTE → DAY_HUNTER_SHOT
 └ END
```

枚举定义在 `backend/game_engine.py` 的 `Phase` 类，顺序表紧跟在后面。新增阶段必须同时处理：枚举、顺序表、`available_actions`、可见性过滤、前端动作表单。

### 1.3 AI 三层策略

| 层 | 实现 | 说明 |
| --- | --- | --- |
| **L0** | `ai_growth.L0Policy`（`L0_NOVICE`） | 非 LLM 的确定性策略，用于全 AI 自对弈基线，零成本可复现 |
| **L1** | `ai_growth.L1RulePolicy`（`L1_RULE`） | 规则策略 + 人格偏置，决定目标排序和发言模板 |
| **L2** | `q_policy.QPolicy`（`L2_STRATEGY`） | 表格型 Q-learning，**只学动作类型**，目标/选项/发言沿用 L1 |

L2 的 Q 表有两版：`l2.qtable.v1`（四维状态）、`l2.qtable.v2`（扩展状态：自身存活、公开票数、公开发言数、女巫药量）。模型 JSON 带 `content_hash`，加载时校验，篡改直接报错。

### 1.4 四种人格

| 枚举 | 中文 | 行为倾向 |
| --- | --- | --- |
| `AGGRESSIVE` | 冲锋型 | 主动带节奏、抢先归票 |
| `STEADY` | 稳健型 | 少出头、跟最强证据、避免分票 |
| `LOGICAL` | 逻辑型 | 抓硬规则矛盾、票型、查验链，按证据归票 |
| `CHAOTIC` | 搅局型 | 反常规目标，制造信息噪声 |

**关键约束**：人格只对**合法目标重新排序**，绝不发明动作或目标。狼队人格强制互补，按 `seed + seat` 稳定分配——同一 seed 复现同一套人格。

### 1.5 三个白名单工具

| 工具 | 作用 |
| --- | --- |
| `audit_logic` | 硬规则矛盾审计（未发言断言神职、一晚两验、金水反投、票死人、号召票某人却投别人） |
| `analyze_votes` | 公开票型分析 |
| `search_tactics` | 检索当前局面可用战术 |

三个工具**都不接受参数**，传参直接拒绝；绑定调用者自身的 `state` 和 `actor`，只读当前玩家可见信息，不可能越权读隐藏身份。

### 1.6 战术晋升闸门

一条 AI 发明的战术要进入正式决策，必须过四关：

1. **200 局同 seed 配对评测**（`MIN_GAMES_FOR_GATE = 200`）
2. **精确 McNemar 双侧检验**（只看不一致对）
3. **效应量 ≥ `AUTO_MIN_DELTA`**
4. 通过后自动闸门记录为 reviewer `auto-gate.v1`，再走**人工审批**（需 `X-Reviewer-Token`）

自动闸门不能替代人工，两者都要过。`candidates/` 目录里的战术不参与正式对局决策。

用户能做的完整链路：

1. **大厅**：创建房间（得到房间号 + 观战密码）、用房间号加入、用观战密码进上帝视角
2. **对局**：按服务器返回的 `available_actions` 点动作，只能选合法目标；倒计时归零后等服务器推进
3. **观战**：只读上帝视角，能看到全部身份和 AI 决策轨迹
4. **策略实验室**：提交候选战术 → 发起 200 局对照评测 → 看 McNemar 结果 → 通过/驳回/回滚
5. **截图复盘**：上传对局截图 → 人工确认识别文本 → AI 按硬规则生成逻辑复盘
6. **赛后**：胜方、九人身份、当前视角可见死因、AI 命中战术与人格标签

**重要**：`build-static.mjs` 已改为**自动遍历 `components/` 目录**（提交 `93a2892`）。新增组件只需放进目录，不用再改构建脚本。之前白屏就是因为它手动列清单漏了新组件。

## 7. 设计约束（改代码前必读）

1. **模型不能改游戏状态。** 只生成候选，服务端 `available_actions` 校验通过才进引擎。
2. **不能读他人隐藏身份。** 检索和工具只读当前玩家可见信息。
3. **不能选服务器没给的目标。** 非法动作记 `AI_ACTION_FAILED` 并回滚。
4. **同 seed + 同动作序列 = 同 AI 事件序列。** 实时房 seed 由服务端生成，浏览器不许用 `Date.now()`。
5. **`.env` 永不入库。** 真实 Key 只写本地和服务器，`.env.example` 只放变量名。
6. **房间数据在进程内存。** 服务重启即清空，不要假设持久化。
7. **房间号区分大小写。** 不要擅自转大小写。

## 9. 成本控制（上一轮踩的坑）

上一轮 Codex 会话把上下文滚到 **1.76 亿 input token**，原因是：

- 单个会话跨两天持续使用，累积 3351 条记录
- 每轮请求都把 48.5 万 token 的完整历史重发给模型
- 21 个用户回合触发 186 次模型调用（每个回合 8~9 步工具调用）

**接手后的做法：**

1. **一个任务一个会话。** 部署完就开新会话做下一件事，不要在一个会话里连续干一整天。
2. **长任务拆成短会话。** 大重构分多次，每次独立会话，靠 `docs/` 和 git commit 传递上下文，不靠聊天历史。
3. **`model_reasoning_effort` 用 medium 就够**，不必 high。
4. **项目自带 `llm_budget.py`**（进程级花费台账），夜间训练前先确认预算上限。
5. **搜索类工具单次输出上限不要开到 30000 token**，5000 足够。

判断标准：如果界面顶部的上下文用量条过半，就该开新会话了。
