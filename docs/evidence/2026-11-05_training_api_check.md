L1 的好人胜率从 **36.5% 掉到 17.0%**，差 39 个胜场，远超抽样波动。

### 3.1 原因定位

`policy_version` 前后都是 `l1.rule.v1`，版本号没变，但行为变了。逐层排查后定位到发言逻辑：

```python
# backend/ai_growth.py  L1 的狼人目标选择依据
@staticmethod
def _claimed_god_ids(state, actor) -> set[str]:
    keywords = ("预言家", "女巫", "猎人")
    ...  # 扫描 PUBLIC_SPEECH / LAST_WORDS 的 content，把自称神职的人记为「已自报神职」
```

而 `speech_content()` 在 10-29 之后被重写为**角色化发言**（`b78c9ab` 起，`d40c42f` 进一步用策略库生成）：

- 旧版：全员「我是N号，先听后续发言。」——**不含任何身份关键词**，`_claimed_god_ids` 恒为空
- 新版：预言家说「我是预言家，今晚我会查验 X」、猎人说「我是猎人，别急着票我」——**关键词命中**

于是 L1 的狼人开始**优先刀公开自报的神职**，好人阵营的预言家/猎人更快出局，好人胜率从 36.5% 跌到 17.0%。

**这是发言逻辑改动的连带效应，不是 L1 策略代码被改。** 从玩法真实性看，狼人冲着自报神职下刀其实更合理；但它让 10-29 的 L1 基准失效了。

**但绝不能因此把 G-06 改成 Go。** 这不是 L2 变强，是 L1 变弱。正确的表述是：**基准失效，跨版本不可比，需重跑基准后重新对照**。

## 六、rollout 接口（不通过）

### 6.1 公网超时

| 请求 | 结果 |
| --- | --- |
| `games=1` | `200`，但耗时 **34.8 秒** |
| `games=2` | **`504 Gateway Time-out`**（nginx 60 秒超时） |
| `games=3` | 客户端 90 秒读超时 |

### 6.2 本地同版本对照

```text
本地 26b746f，games=2 → 200，耗时 0.1 秒
{"good_wins":1,"wolf_wins":1,"good_win_rate":0.5,
 "confidence_interval_95":[0.0945,0.9055],"delta_good_win_rate":0.0}
```

**同一份代码，本地 0.1 秒，公网 34.8 秒，差 300 倍以上。** 这不是代码问题，是公网环境问题。

### 6.3 可能原因（需订书机确认）

1. **公网启用了 LLM 发言**（`WOLFARENA_LLM_SPEECH`，`95242e7` 引入）。rollout 是全 AI 自博弈，若每句话都要请求模型，一局几十次调用，30 秒完全对得上。这是最可能的原因。
2. 公网 ECS 配置过低（单核），但单核也解释不了 300 倍差距。
3. 公网进程同时扛着多房间定时器，CPU 被占满。

### 6.4 影响与建议

演示时若点「胜率 rollout」，**2 局以上必定 504**，会很难看。

建议三选一：

- 把 `games` 上限从 100 降到 10，并在页面上标注「约 10 秒/局」
- 改成异步：返回 job id，前端轮询结果
- 若确实是 LLM 发言导致，rollout 内部强制关闭 LLM 发言（全 AI 自博弈不需要真实发言）

同时把 nginx 的 `proxy_read_timeout` 从默认 60 秒调大，避免 504 直接暴露给评审。

## 七、给订书机的三条

**1. L1 基准要重跑，并且给版本号。** 发言逻辑改动影响了 L1 的决策，但 `policy_version` 仍是 `l1.rule.v1`，从版本号看不出差异。建议：重跑 L1 200 局、更新 manifest 与 `/api/training/metrics` 的数据源，并把版本号改成 `l1.rule.v2`，否则以后每改一次发言都会悄悄改变基准。

**2. 文档里的「L2 未超 L1」要改写。** 现在这句话与数据矛盾：按当前代码 L2（35.0%）高于 L1（17.0%）。正确表述是「L1 基准随发言逻辑变更失效，三策略需在同一版本下重跑后才能比较；L2 相对旧基准的提升不成立」。**G-06 仍维持 No-Go，但理由要换。**

**3. rollout 接口必须能在公网用。** 现在 2 局就 504。优先查公网是否开了 LLM 发言。
